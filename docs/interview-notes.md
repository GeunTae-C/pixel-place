# pixel-place 면접 답변 노트

작성 기준: 2026-11-10. 프로젝트의 구현 범위와 판단을 자신의 말로 설명하기 위한 답변을 주제별로 모은다.

## 01. HTTP 요청이 먼저 도착한 순서까지 보장하지 않는 이유

**질문:** 서로 다른 사용자가 같은 픽셀을 변경할 때, 먼저 도착한 요청부터 처리되나요? HTTP 도착 순서를 보장하지 않는 이유는 무엇인가요?

### 면접 답변

현재 기본 group 경로에서는 검증을 통과해 쓰기 큐에 게시된 순서를 기준으로 처리하고, 그 순서를 WAL 기록과 메모리 반영에 일관되게 연결합니다. 다만 인증이나 쿨다운 확인에 걸리는 시간이 요청마다 달라서 HTTP 요청의 최초 도착 순서까지 보장하지는 않습니다. 같은 픽셀에 대한 요청도 이 기준을 따릅니다.

이 범위를 선착순까지 넓히는 방안도 검토했습니다. 순번만 붙이는 것으로 끝나지 않고, 앞 요청의 거절·취소·시간 초과, 사용자별 gate와의 관계, 대기열 한도와 종료 처리까지 함께 설계해야 합니다. 그래서 현재는 기존 쓰기·복구 계약을 유지하고, 선착순이 실제 서비스 요구사항이 되면 별도 변경으로 구현하고 검증하는 것이 적절하다고 판단했습니다. 두 방식의 성능을 직접 비교한 것은 아닙니다.

### 설명할 때 지킬 경계

- **보장 기준:** 현재 기본 group 경로의 FIFO 게시 순서다. HTTP 최초 접수 순서나 같은 픽셀의 HTTP 선착순 보장으로 넓혀 말하지 않는다. 큐에서 처리 전 취소될 수 있는 요청까지 모두 성공한다는 뜻도 아니다.
- **현재 판단:** 선착순 요구를 추가하려면 기존 동시성·실패·종료 계약과 함께 검증해야 한다는 판단이다. 최초 구현 당시부터 이 비교를 마쳤다고 설명하지 않는다.
- **성능:** 선착순 방식과 직접 비교한 자료가 없으므로 더 빠르다거나 몇 ms 절약했다고 말하지 않는다.
